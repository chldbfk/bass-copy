# 타브 악보 자동 생성 앱 — 작업 계획서

> 관련 문서: [1차 아이디어.md](./1차 아이디어.md)

---

## 1. 프로젝트 개요
- **한 줄 정의**: 사용자가 원하는 곡을 업로드하면 AI가 악기별(베이스/기타/드럼) TAB 악보를 자동 생성해주는 앱
- **핵심 타겟**: 비전공자·음악 취미생, 특히 베이스·일렉기타·통기타 연주자
- **핵심 Pain Point**: 정식 악보가 없는 곡은 귀카피를 해야 하는데, 이 과정이 번거롭고 진입장벽이 높음

### 1-1. 경쟁사 분석 — Ultimate Guitar

**개요**: 기타/베이스 TAB과 코드보를 다루는 가장 큰 사이트(ultimate-guitar.com). 웹+앱으로 서비스하며, 오랫동안 TAB 시장의 사실상 표준 플랫폼 역할을 해옴

**운영 방식**
- **크라우드소싱 TAB**: 일반 유저가 직접 곡을 듣고 채보해서 업로드하는 방식(위키형 아카이브). 같은 곡도 여러 버전이 올라오고 퀄리티가 사람마다 제각각
- **Official Tabs**: 저작권사와 정식 라이선스 계약을 맺어 제공하는 공식 악보. 크라우드소싱보다 정확도는 높지만 유료 구독(Ultimate Guitar Pro) 필요
- **부가 기능**: 자동 스크롤, 템포 조절, 튜너, Guitar Pro 파일(.gp) 지원, 코드 다이어그램 등

**강점**
- 압도적인 곡 커버리지(오랜 기간 쌓인 유저 기여 데이터)와 브랜드 인지도
- 무료로 대부분의 크라우드소싱 TAB 이용 가능
- 이미 확립된 커뮤니티/생태계

**약점 (우리의 기회)**
- 모든 TAB이 **사람이 직접 채보**한 결과물 → 제작에 시간이 걸려서 최신곡·마이너 곡·비영어권 곡은 아무도 안 만들면 아예 없음
- 크라우드소싱 TAB은 채보자 실력에 따라 **정확도가 들쭉날쭉** (오타, 잘못된 프렛 표기, 리듬 누락 등)
- Official Tab은 정확도는 높지만 **유명곡 위주**라 커버리지가 제한적이고, 유료 구독이 필요
- **자동화가 전혀 없음** → 원하는 곡이 없으면 사용자가 스스로 채보하거나 포기해야 함

**우리 앱의 보완 포인트**
1. **커버리지 공백 해소**: AI 자동 생성이므로 사람이 아직 안 만든 곡도 몇 분 만에 TAB 확보 가능 → Ultimate Guitar가 구조적으로 못 채우는 최신곡/마이너 곡 수요를 정조준
2. **일관된 품질**: 채보자 개인 실력에 좌우되지 않고, 알고리즘 기준으로 일관된 정확도 제공 (다만 초기엔 AI 정확도 자체가 사람 채보보다 낮을 수 있어 검증 필요)
3. **속도**: 사람이 채보하는 데 걸리는 시간(몇 시간~며칠) 대비 AI는 몇 분 내 처리 가능
4. **포지셔닝**: Ultimate Guitar를 완전히 대체하기보다, "없는 곡을 즉시 만들어주는" 보완재로 시작해서 점진적으로 정확도를 끌어올리는 전략이 현실적

### 1-2. 경쟁사 분석 — AI 기반 서비스 (Moises 등)

**개요**: Moises는 이미 AI 기반 스템 분리(보컬/드럼/베이스/기타 등), 코드 인식, 키·템포 감지, 보컬 리무버 등을 제공하는 음악 연습 앱. Ultimate Guitar와 달리 AI 자동화를 이미 상용화한 상태라 우리와 가장 직접적으로 경쟁하는 서비스

**강점**
- AI 기반 자동화를 이미 시장에 내놓은 선점 효과, 큰 사용자 기반
- 스템 분리 + 코드 인식 + 템포/키 감지 + 연습 도구(메트로놈, 피치 변경 등)를 통합 제공
- 크로스플랫폼(웹/모바일)

**약점 (우리의 기회)**
- 제공하는 건 **코드 차트/코드 진행** 수준이지, 실제 연주 가능한 **음표 단위 TAB(프렛-스트링 세부 표기)**은 아님 — 즉 "이 구간은 C코드"까지는 알려줘도 "정확히 몇 번째 줄 몇 프렛을 짚어야 하는지"는 제공하지 않음
- 운지(핑거링) 최적화 개념이 없어 실제 연주 동선을 고려한 세부 악보로 이어지지 않음
- 베이스 라인처럼 멜로디/리프 단위의 정밀한 노트 시퀀스 추출에는 특화되어 있지 않음

**우리 앱과의 차별점**
- Moises: "이 곡의 코드가 뭔지" 알려주는 도구 → 우리: "이 곡을 실제로 어떻게 손으로 짚어서 연주하는지" 알려주는 도구
- 즉, Moises는 코드 반주 학습에 가깝고, 우리는 리프/멜로디 단위의 정밀 TAB 생성에 집중 → 겹치는 시장이 아니라 인접 시장에서 더 세밀한 니즈를 파고드는 포지셔닝

## 2. MVP 목표
**"곡 하나를 업로드하면 베이스 라인 TAB 악보가 자동으로 생성된다"**
— 가장 좁은 범위로 시작해서 핵심 가설(AI로 쓸만한 TAB을 뽑을 수 있는가)부터 검증

## 3. MVP 범위

### 포함 (Scope In)
- **악기**: 베이스만 우선 지원 (모노포닉이라 전사 난이도가 낮아 가장 빠르게 결과물을 낼 수 있음)
- **입력**: 사용자 직접 음원 파일 업로드
- **출력**: 기본 TAB 표기 (프렛 번호 + 기본 리듬)
- **재생 연동**: 원곡 오디오 재생에 맞춘 TAB 자동 스크롤 — AMT 단계에서 이미 추출한 음별 타이밍(온셋) 데이터를 재사용하면 되므로 추가 데이터 없이 구현 가능, MVP 포함 권장
- **결과 수정(편집) 기능**: AI가 생성한 TAB이 틀렸을 때 사용자가 직접 프렛 번호를 고칠 수 있는 간단한 편집 기능 — AI 정확도가 100%일 수 없다는 걸 감안하면 신뢰 확보를 위해 MVP에 필요. 복잡한 편집 툴 대신, 음표 단위로 프렛 값을 클릭해서 수정하는 최소 기능으로 시작
- **플랫폼**: 웹 앱

### 제외 (Scope Out — 이후 단계로)
- 기타·드럼 TAB
- 유튜브 링크 지원 (저작권/ToS 이슈로 초기 제외)
- 회원가입/결제 시스템
- 커뮤니티·공유 기능
- 벤딩/슬라이드 등 고급 주법 표기

## 4. 기술 스택 (파이프라인 단계별)

| 단계 | 필요 기술 | 비고 |
|---|---|---|
| 음원 분리 | Demucs(Meta) 또는 Spleeter(Deezer) | 둘 다 오픈소스(MIT 라이선스), 상업적 이용 가능. Demucs가 현재 SOTA |
| 음정·리듬 검출 (AMT) | 베이스/보컬: CREPE, pYIN / 범용: Spotify Basic Pitch, Google MT3·Onsets and Frames | 베이스(모노포닉)는 정확도 높음, 기타(폴리포닉)는 난이도 높음 |
| 드럼 전사 | 별도 ADT(Automatic Drum Transcription) 모델 | MVP 범위 밖, Phase 3 고려 |
| 노트 → TAB 변환 | 운지 최적화 알고리즘(동적계획법 기반), 코드 인식 결합 | 기타/베이스 TAB 생성만의 특수 과제 |
| 악보 렌더링 | AlphaTab, VexFlow | Guitar Pro(.gp)/MusicXML export 고려 |
| 인프라 | GPU 서버, 비동기 큐 처리 | Phase 0은 Google Colab 무료 GPU로 시작 가능 |

**리스크**: 음원 분리 기술 자체는 오픈소스이나, 처리 대상인 원곡 음원의 저작권 문제는 별개 — 개인 학습용 명시 또는 저작권사 제휴 검토 필요

### 4-1. 노트 → TAB 변환 상세 — 연주하기 편한 운지 알고리즘

**문제 정의**: 같은 음을 낼 수 있는 여러 (줄, 프렛) 후보 중, 실제 연주자가 편하게 이어칠 수 있는 조합을 선택해야 함

**접근 방식**: 비용 함수(cost function) + 최단 경로 탐색
- 각 음표마다 가능한 (줄, 프렛) 후보를 노드로, 연속된 두 음표 사이 이동 비용을 edge weight로 정의
- 곡 전체에서 누적 비용이 최소가 되는 경로를 동적계획법(DP)/다익스트라로 탐색
- 음표 하나씩 그리디하게 고르면 안 됨 — 당장은 편해도 다음 음에서 큰 이동이 필요해질 수 있어, 전체 구간을 보고 최적화 필요

**비용 함수에 들어갈 요소**
1. 프렛 이동 거리 — 연속 음 사이 프렛 번호 차이가 클수록 페널티
2. 줄 변경 페널티 — 불필요한 줄 이동 억제, 같은 줄/인접 줄 유지 선호
3. 오픈 스트링 선호 — 개방현은 손가락 부담이 없으므로 우선 배치
4. 포지션(구역) 유지 — 손을 한 자리(보통 4프렛 범위)에 고정하는 걸 선호, 포지션 이탈 시 추가 페널티
5. (기타 코드 한정) 손 스팬 제약 — 동시에 눌러야 하는 음들이 물리적으로 가능한 범위인지 체크

**베이스(MVP 범위) 기준 단순화**: 대부분 모노포닉이라 코드 손 스팬 문제는 없음 → 프렛 이동 거리 최소화 + 줄 변경 억제 + 오픈 스트링 선호, 이 세 가지 가중치 조합만으로도 꽤 자연스러운 결과 기대 가능

**검증/보정 방법**: 초기엔 직관적 가중치로 시작해 실제 곡에 테스트 후 튜닝, 여유가 되면 기존 크라우드소싱 TAB(Ultimate Guitar 등)을 정답 데이터 삼아 가중치 보정 → 데이터가 쌓이면 학습 기반 접근으로 발전 가능

### 4-2. 음표·주법 표기 정밀도 확장 로드맵

MVP에서 제외한 "고급 주법 표기"를 난이도별로 세분화하면 아래와 같음

**Phase 1~2 수준 (상대적으로 쉬움)**
- 음표 길이(리듬) 정밀도: 4분/8분/16분음표, 셋잇단음표 등 — AMT의 onset/offset 타이밍을 박자 단위로 양자화(quantize)하면 구현 가능
- 셈여림(다이내믹스): 음량(velocity) 정보를 추출해 강세 표시에 반영 가능

**Phase 2~3 수준 (기존 기술 스택의 후처리로 확장 가능)**
- 벤딩·슬라이드: CREPE/Basic Pitch는 프레임 단위 연속 피치 트래킹을 하므로, 음이 순간이 아니라 부드럽게 변하는 구간을 감지하는 휴리스틱을 추가하면 판별 가능 — 새 기술 도입이 아니라 후처리 로직 추가에 가까움
- 비브라토: 피치가 주기적으로 미세하게 흔들리는 패턴 감지로 가능
- 해머링/풀오프: 같은 줄에서 음이 바뀌었는데 새로운 피킹 어택(스펙트럴 플럭스 등)이 감지되지 않으면 해머링/풀오프로 추정

**더 어려운 영역 (별도 모델 학습 필요)**
- 팜뮤트, 고스트 노트 등은 음정이 아닌 음색(timbre)·배음 구조 분석이 필요 — 기존 파이프라인만으론 부족, 별도 분류 모델 학습이 필요한 영역이라 우선순위 후순위

## 5. 로드맵

| 단계 | 기간(예상) | 내용 |
|---|---|---|
| Phase 0: 기술 PoC | 2~4주 | Demucs+Basic Pitch 조합 테스트, 실제 곡 몇 개로 정확도 확인, 운지 최적화 알고리즘 프로토타입 |
| Phase 1: MVP 개발 | 6~8주 | 업로드→처리→TAB 뷰어까지 엔드투엔드 웹앱 구축 |
| Phase 2: 베타 테스트 | 2~4주 | 동아리 내부/지인 대상 테스트, 정확도·사용성 피드백 수집 |
| Phase 3: 확장 | 이후 | 기타 지원 추가, 유료화 모델, 커뮤니티 기능 |

### 5-1. Phase 3 상세 — AI+커뮤니티 하이브리드 공용 악보 저장소

**아이디어 출발점**: 악보바다 등에서 실제로 돈을 받고 사람이 직접 채보해주는 서비스가 존재한다는 건, 채보 자체에 시장 지불 의사가 있다는 방증. 이걸 "AI 초안 + 사람 보정"으로 대체하면 비용은 낮추고 속도는 높일 수 있음

**동작 방식**
1. 사용자가 곡을 업로드하면 AI가 TAB 초안을 생성
2. 요청한 사용자가 편집 기능(3번 섹션에서 정의한 결과 수정 기능)으로 오류를 직접 보정
3. 보정된 TAB을 앱 내 공용 저장소(커뮤니티 카테고리)에 업로드
4. 이후 동일한 곡을 다른 사용자가 요청하면, AI를 다시 돌리지 않고 저장소에 있는 검증된 TAB을 즉시 제공

**기대 효과**
- **연산 비용 절감**: 같은 곡을 여러 명이 각자 AI로 재처리하는 낭비 제거
- **정확도 향상**: 사람이 한 번 보정한 결과가 쌓이므로, 시간이 지날수록 저장소 전체의 품질이 AI 단독 결과보다 높아짐
- **네트워크 효과**: 곡 라이브러리가 누적될수록 신규 사용자 입장에서 앱의 가치가 커짐 (Ultimate Guitar가 오랜 기간 쌓은 자산과 유사한 구조를, AI로 시작 속도를 훨씬 앞당겨서 구축)

**주의할 점 — 저작권 리스크 상향**
- 8번 섹션의 데이터 정책은 "개인 학습용, 원본 음원 삭제"를 전제로 리스크를 낮춰뒀는데, **공용 저장소에 TAB을 공개 업로드하는 순간 개인적 이용의 범위를 넘어서 저작권 리스크가 커짐**
- TAB 자체는 원곡의 완전한 복제가 아니라 법적 회색지대이고 Ultimate Guitar도 이 기반으로 운영되고 있지만, 실제로 이 기능을 붙이는 시점(Phase 3)에는 별도의 저작권 리스크 검토가 선행되어야 함

### 5-2. 수익화 방안 — 하이브리드 구조 기반

**핵심 아이디어**: "새로 AI 생성하는 것"과 "저장소에서 조회하는 것"은 비용 구조가 다름(전자는 GPU 연산 비용 발생, 후자는 거의 무비용) → 이 차이를 그대로 과금 기준으로 활용

**기본 모델: 비용이 드는 지점만 유료화**
- 무료: 저장소에 이미 있는(다른 사용자가 만들고 검증한) TAB 조회는 무제한 — 네트워크 효과 극대화
- 유료: 저장소에 없는 새 곡을 AI로 처음 생성하는 요청에만 크레딧/구독 과금 — 실제 비용이 드는 지점에서만 과금하므로 합리적

**기여자 인센티브 (공급 측 순환 구조)**
- AI 초안을 보정해서 저장소에 업로드하면 무료 생성 크레딧 지급 → 저장소가 빠르게 채워지고, 유료 생성 요청은 자연스럽게 "아직 아무도 안 만든 희귀곡"으로 집중되어 서버 부담도 관리됨

**추가 수익원**
- 저장소 조회(무료 티어)에 광고 삽입
- 프리미엄 구독: 무제한 생성, 우선 처리 큐, 광고 제거, PDF/Guitar Pro 파일 export
- 커뮤니티 규모 확대 시 학원·밴드 단체 대상 B2B 라이선스로 확장 (1차 아이디어 문서의 수익화 방향과 연결)

## 9. Phase 0 PoC 진행 기록

실제 곡("일당백 - 데카당", 65초 클립)으로 로컬 환경(Python 3.13, CPU 전용)에서 파이프라인을 처음부터 끝까지 돌려본 기록.

### 9-1. 환경/기술 스택 변경 사항
- **basic-pitch 대체**: 계획했던 Spotify Basic Pitch는 Python 3.13과 numpy 버전 호환 문제로 설치 불가 → 베이스는 모노포닉이므로 **torchcrepe**(PyTorch 기반 CREPE)로 대체. 순수 PyTorch 구현이라 최신 Python 환경에서도 설치가 깔끔함
- Demucs, ffmpeg(winget으로 설치)는 계획대로 정상 동작

### 9-2. 발견한 버그 — torchcrepe FMIN 음수 인덱스 버그
- torchcrepe 0.0.24에서 FMIN을 너무 낮게 잡으면(예: 30Hz) 내부적으로 음수 bin 인덱스가 나오는데, 이게 파이썬 배열 슬라이싱에서 "끝에서부터"로 잘못 해석되며 전체 확률 마스킹이 깨져 모든 결과가 무의미해지는 문제 발견
- **해결**: FMIN을 35Hz로 조정(베이스 최저음 E1=41.2Hz보다 낮아 커버리지 문제없음). 라이브러리 버전 업데이트 전까지는 이 하한선을 유지할 것

### 9-3. 운지 최적화 비용 함수 — 두 번의 튜닝 시행착오
1. **1차 시도(줄 변경 페널티 소폭)**: 결과가 줄을 너무 자주 옮겨 다녀 "운지하기 힘들다"는 피드백
2. **2차 시도(줄 변경 페널티 대폭 상향)**: 원곡 TAB과 대조해 "한 줄에서 슬라이드로 쭉 이어가는" 패턴이 많다고 판단해 반영했으나, 실제로는 정반대 원인으로 여전히 부자연스러웠음
3. **최종(포지션 박스 방식)**: 실제 베이스 운지의 핵심은 "줄을 안 바꾸는 것"이 아니라 **손 위치(3~4프렛 범위)를 유지한 채 4개 손가락으로 여러 줄을 자유롭게 넘나드는 것**이었음. 같은 음이 다른 줄에도 존재하므로, 포지션 박스 안에서는 줄 변경이 사실상 무비용이고, 포지션 박스를 벗어날 때만 실제 손 이동 비용이 발생하도록 비용 함수를 재설계 → 결과가 크게 자연스러워짐 (4-1 섹션의 비용 함수 요소 중 "포지션 유지"가 실제로는 "줄 변경 억제"보다 훨씬 지배적인 요소임을 확인)

### 9-4. 조성(key) 추정 기반 오류 검출 — 실험 결과
- 사용자 제안으로 "효율적 운지에는 스케일(음악 이론) 지식이 필요하다"는 아이디어를 실험
- 추출된 노트의 음이름 분포에 **Krumhansl-Schmuckler 키 추정 알고리즘**을 적용해 곡의 조성을 자동 추정 → **G minor로 추정(상관계수 0.848)**, 원곡 PDF의 실제 코드 진행(Gm7 기반)과 정확히 일치해 이 방식의 유효성을 확인
- 추정된 스케일에 속하지 않는 음을 검사한 결과, 251개 노트 중 11개가 스케일 밖이었고 그중 10개가 **극히 짧은 길이(0.06~0.17초, 대부분 0.1초 미만)**였음 → "스케일 밖 + 극히 짧음"을 노이즈 후보 판정 기준으로 사용해 필터링, 241개로 정리
- **활용 방향**: 스케일 정보 자체가 프렛/줄 선택을 바꾸지는 않지만(감지된 피치는 고정값이므로), (1) 피치 검출 오류 후보를 자동으로 걸러내는 품질 필터로 유용함을 확인. (2) 코드 진행을 알면(원곡처럼) 구간별 조성이 바뀌는 것까지 반영할 수 있어 정확도를 더 높일 여지가 있음 — 다만 이번엔 곡 전체를 단일 조성으로 가정한 단순화 버전이라 코드 전환 구간에서는 오탐 가능성이 있음. 실서비스에서는 정식 코드 인식(chord recognition) 모델과 결합해야 구간별 정확도를 확보할 수 있음(4-1 섹션 "코드 인식 결합" 항목과 연결)

### 9-4-1. 국소 앵커 기반 2차 운지 최적화 — 스케일 정보의 실질적 반영 방식
- 스케일 소속 여부 자체는 (같은 음이면 어느 프렛을 골라도 음이 동일하므로) 프렛/줄 선택에 직접 영향을 줄 수 없다는 한계를 확인 → 대신 스케일 필터링으로 정제된 안정적인 노트 시퀀스를 활용해 **2단계(two-pass) DP**로 접근
  1. 1차: 기존 인접-노트 기반 포지션 박스 DP로 기준 경로 산출
  2. 2차: 1차 결과에서 구간별(앞뒤 3개 노트 윈도우) 대표 프렛(중앙값)을 "국소 앵커"로 계산 → 앵커에서 멀어질수록 추가 비용을 부여해 재최적화
- **효과 확인**: 불필요하게 멀리 뻗은 프렛 선택(예: E현 6프렛)이 주변 구간에서 이미 쓰이던 낮은 포지션의 대체 운지(A현 1프렛, 동일 음)로 재배치됨. 고음역 솔로 구간(15~17프렛)도 이전보다 하나의 포지션 박스 안에서 더 일관되게 유지됨
- 즉 "스케일을 안다"는 것의 실질적 기여는 프렛 자체를 결정하는 게 아니라, **노이즈를 제거해 신뢰할 수 있는 시퀀스를 만들고, 그 시퀀스의 국소적 안정성을 앵커로 활용해 포지션 박스를 오래 유지하도록 유도하는 것**이었음

### 9-5. 종합 평가
- 음원 분리 → 피치 추출 → 스케일 기반 노이즈 필터링 → 운지 최적화 → TAB 렌더링까지 **엔드투엔드 파이프라인이 로컬 CPU 환경에서 동작함을 확인**
- 원곡 공식 TAB과 대조했을 때 코드 진행에 따른 저음역대 이동, 하이라이트 구간(17프렛까지 올라가는 솔로성 프레이즈)의 존재 등 구조적으로 유사한 결과를 얻음
- 남은 과제: 리듬(박자) 정렬, 슬라이드/해머링 등 주법 표기(4-2 섹션 참고), 구간별 코드 인식을 통한 조성 추정 고도화

### 9-6. 리듬(박자) 정렬 추가
- librosa의 비트 트래킹(`librosa.beat.beat_track`)으로 오디오에서 템포(BPM)와 비트 타임스탬프를 직접 추정 → 일당백 - 데카당 곡에서 **92.3 BPM, 비트 99개** 감지
- 4/4 박자를 가정하고, 감지된 비트를 기준으로 각 노트를 마디 번호·마디 내 박자 위치로 변환, 노트 길이는 비트 길이 대비 비율로 표준 음표(온음표~32분음표, 점음표 포함) 중 가장 가까운 값에 매핑
- 이 결과를 운지 최적화 결과와 결합해 **마디선이 있는 최종 TAB**을 렌더링(`poc_final_tab.py`) → 4마디 단위로 반복되는 Gm7-C7-Cm7-D7 진행이 실제로 마디 1과 마디 3에서 거의 동일한 패턴으로 재현되는 것을 확인, 원곡 구조와 부합
- **검증이 더 필요한 부분**: 92.3 BPM 기준으로 계산했을 때 32분음표로 분류되는 노트가 상당히 많음 — 실제로 그렇게 빠른 프레이즈인지, 아니면 노트 길이 검출 자체가 짧게 잡히는 경향(트랜지언트 경계 처리) 때문에 과도하게 잘게 분류되는 것인지 추가 검증 필요

### 9-7. 시각화 — AlphaTab 통합
- 처음엔 ASCII TAB, 이후 직접 그린 SVG(음표/쉼표 기호 수작업 구현)로 시각화 → 사용자가 실제 원곡 TAB 캡처를 기준으로 "빔 연결, 슬러 등 전문 엔진 수준 필요"라고 지적, **AlphaTab**(오픈소스 악보 렌더링 라이브러리) 통합으로 전환
- 파이프라인 결과를 **MusicXML**로 변환하는 모듈(`poc_export_musicxml.py`)을 새로 작성 — 조표(fifths), 음이름 스펠링(장조/단조에 맞는 샵/플랫 선택), 마디당 duration 합계를 정확히 맞추는 비례 재조정(rescale) 로직 포함
- AlphaTab JS(1MB)와 Bravura 폰트를 전부 base64/inline으로 임베드해 외부 네트워크 요청 없이 동작하는 단일 HTML 생성(`poc_export_alphatab_html.py`) — Artifact 환경의 CSP(외부 요청 차단) 제약 때문
- **디버깅 과정에서 실제 버그 3개 발견 및 수정**:
  1. `settings.core.useWorkers` 기본값(true)이 Web Worker를 쓰려다 인라인 스크립트 환경에서 실패 → false로 비활성화
  2. `<clef>`를 일반 베이스 클레프(F)로 지정해 AlphaTab이 이 스태프를 표준 오선 스태프로 인식 → **TAB 클레프**(`<sign>TAB</sign>`)로 수정해야 TAB 전용 모드에서 렌더링됨
  3. `<staff-tuning>` 요소가 `<staff-details>` 밖에 형제 태그로 빠져나와 있어 튜닝 정보가 비어있던 XML 중첩 버그 → 중첩 수정 후 실제 TAB이 렌더링되기 시작함
- `StaveProfile.Tab` + `TabRhythmMode.ShowWithBeams` 설정으로 "오선보 없이 TAB 숫자에 리듬 기둥/꼬리만 붙는" Songsterr 스타일 렌더링 확인
- **미해결 이슈**: 같은 박 안의 연속된 짧은 음표들을 빔으로 묶으려고 MusicXML에 `<beam>` 요소(begin/continue/end)를 박자 단위로 직접 계산해 넣었고, AlphaTab이 이를 파싱해 노트별 `beamingMode`(ForceMergeWithNext 등)로 반영하는 것까지 코드 레벨에서 확인했으나, TAB 전용 리듬 오버레이 렌더링 경로가 이 값을 실제로 참조하는지는 확인 불가(비공식 압축 코드 한계) — 현재는 음표가 개별 꼬리로 표시됨(기능적으로는 정상, 시각적 완성도만 아쉬움)

### 9-8. 실제 앱 아키텍처와의 관계
- 오늘 만든 구조(백엔드가 MusicXML 생성 → 클라이언트에서 AlphaTab이 렌더링)는 **실제 서비스에도 그대로 적용 가능한 아키텍처**임을 확인
- 단, AlphaTab을 통째로 인라인 임베드한 것은 Artifact의 CSP 제약 때문의 임시 조치 — 실제 웹앱에서는 일반적인 스크립트 로딩 방식으로 훨씬 단순해짐
- 커맨드라인 스크립트 → 업로드 API 엔드포인트로의 전환, GPU 서버·비동기 큐 처리는 이미 계획서에 있던 Phase 1 항목과 동일

### 9-9. AlphaTab 빔 그룹핑 이슈 해결
- AlphaTab GitHub 저장소(`CoderLine/alphaTab`)를 직접 클론해 비압축 소스코드로 원인 확인
- `TabRhythmMode.ShowWithBeams`는 이름과 반대로 **항상 개별 꼬리(플래그)로만 그리도록 강제**하는 옵션이었고(`TabBarRenderer.drawBeamHelperAsFlags`에서 `|| rhythmMode===ShowWithBeams`로 무조건 true 반환), 실제로 정상적인 빔 그룹핑 로직을 따르는 건 **`TabRhythmMode.ShowWithBars`**였음(라이브러리의 "TAB 전용일 때 자동 선택되는 기본값"도 실제로 ShowWithBars였음)
- 설정 변경 후 박자 단위로 정상적으로 묶인 빔 렌더링 확인됨 — MusicXML에 직접 넣은 `<beam>` 요소(begin/continue/end)가 정확히 반영됨
- **교훈**: 압축된 소스만으로 추측하는 것보다 실제 GitHub 소스를 직접 받아서 확인하는 게 훨씬 빠르고 정확함(내일 작업 계획에서 이걸 미리 준비해둔 게 유효했음)

### 9-10. 템포(BPM) 자동 감지의 신뢰도 문제
- 오디티스 곡 검증 중 사용자가 실제 BPM(78)을 알려줬는데, librosa 자동 감지 결과는 베이스 단독 트랙 기준와 전체 믹스 기준이 서로 다르고(각각 다른 값), 둘 다 78과도 불일치 — 78과 전체 믹스 감지값(103.4)은 대략 3:4 비율로, 흔한 "옥타브 오류"(펄스를 다른 배음 단위로 잘못 잡는 문제) 패턴과 일치
- **원인**: 온셋 주기성 기반 비트 트래킹은 태생적으로 옥타브 오류에 취약하고, 타격이 뚜렷한 곡(드럼 비트 강함)일수록 정확도가 높고 레가토/당김음이 많은 곡일수록 부정확해짐
- **중요한 재인식**: 일당백 사례에서 "92.3 BPM이 검증됐다"는 것도 사실은 원곡 PDF의 마디 구조와 대조해 "그럴듯하다"고 판단한 것이지, 정확한 BPM 수치 자체를 공식 자료로 검증한 건 아니었음 — 자동 감지가 항상 신뢰할 수 있다고 가정하면 안 됨
- **제품 시사점**: 실서비스에서는 자동 템포 감지에만 의존하지 말고, **사용자가 직접 BPM을 입력·수정할 수 있는 기능**(수동 오버라이드)이 필요함. PoC 코드에도 `override_bpm` 파라미터를 임시로 추가해 검증함(`poc_export_musicxml.py`)

## 11. 악보 생성 품질 기준

**왜 이 섹션이 필요한가**: 지금까지는 곡 하나씩 돌려보면서 문제가 터지면 그때그때 고쳐왔는데(BPM 옥타브 오류, 인트로/아웃트로 노이즈, 슬라이드 오탐 등), 최종 목표는 이 파이프라인을 **앱으로 출시**하는 것이므로 "어느 정도 정확도/안정성이면 이 기능을 제품에 넣어도 되는가"에 대한 기준이 필요하다. 아래는 곡별 작업을 반복하면서 항목별로 기준을 채워나가는 진행 중인 목록 — 항목마다 "아는 것"(이미 검증/구현됨)과 "정할 것"(아직 논의/결정 필요)으로 구분한다.

### 11-1. 피치(음정) 인식
- 아는 것: torchcrepe periodicity 임계값 0.5, 최소 노트 길이 0.06s, FMIN 35Hz 하한(`poc_pitch_extract.py`)
- ✅ 방향 결정됨: 정확도를 지금 시점에 어떤 숫자로 미리 정의하기보다, **정확도를 쌓아가는 루프 자체**를 기준으로 삼는다.
  - **출시 전**: 최대한 많은/다양한 곡을 실제로 악보로 만들어보면서, 사용자가 직접 고쳐주는 검증 데이터를 쌓는다(color_mixed 세션의 diff 검증 방식이 축소판). 한 곡을 완벽하게 만드는 데 매몰되지 말고 곡 수를 늘려서 다양한 실패 패턴(장르·주법별)을 최대한 많이 겪어보는 게 우선.
  - **출시 후**: 5-1 섹션의 "AI+커뮤니티 하이브리드" 구상과 동일한 루프 — 실사용자가 생성된 TAB을 수정하면서 쌓이는 데이터를 바탕으로 정확도 수치/임계값을 계속 세밀하게 조정. 즉 정확도 목표치는 미리 추상적으로 정하는 게 아니라, 이 누적 데이터에서 자연스럽게 도출·개선해나간다.
  - 계획서 6번(성공 지표)의 "베타테스터 체감" 기준은 최종 제품 성공 지표로 유지, 이 루프는 그걸 달성하기 위한 엔진.

### 11-2. BPM/리듬
- 아는 것: `librosa.beat.beat_track` 자동감지가 옥타브 오류(2배·3:4 등)에 취약함, `override_bpm` 파라미터로 수동 교정 가능(`poc_export_musicxml.py`)
- ✅ UX 방향 결정됨(구현은 아직 안 함):
  - 생성 전에 필수로 확인받지 않고, **자동감지값으로 먼저 악보를 생성**한 뒤 감지된 BPM을 눈에 잘 띄게 표시
  - 옥타브 오류가 가장 흔한 실패 패턴이므로 "절반으로/두 배로" 같은 빠른 교정 버튼을 우선 제공, 탭 템포(박자에 맞춰 두드려서 BPM 계산)는 있으면 좋지만 MVP 필수는 아님
  - **중요한 전제**: 이 사후 수정 UX는 어디까지나 안전장치이지, 이게 있다고 자동감지 정확도 자체를 안 높여도 되는 건 아님 — 목표는 애초에 오류가 최대한 안 나게 만드는 것. 감지 정확도 자체를 높이는 방법(예: 템포그램 피크 강도로 신뢰도 추정, 드럼 트랙 있으면 그걸로 교차검증 등)은 별도로 계속 찾아야 함

### 11-3. 노이즈/무음 구간 판별
세 구간으로 나눠서 순서대로 다룬다: **3-2 → 3-1 → 3-3**

- **3-2. 짧고 애매한 노트가 노이즈인지 특수 주법(팜뮤트·고스트노트·뮤트 등)인지** — ✅ 결론 남:
  - 스케일 밖+짧다는 이유만으로 지워지던 문제는 이미 해결(`find_chromatic_runs`로 크로매틱 경과음 보호, `poc_tab_render.py`)
  - 단, 팜뮤트/고스트노트/뮤트는 애초에 음정이 뚜렷하지 않아 `PERIODICITY_THRESHOLD=0.5`(첫 관문, `poc_pitch_extract.py`)에서 노트로 만들어지지도 않고 조용히 사라지고 있을 가능성이 있는데, **실제로 얼마나 버려지는지 한 번도 측정한 적이 없음**
  - **다음 액션**: 기존에 처리한 곡(color_mixed 또는 오디티스) 하나를 잡아 periodicity<0.5로 버려지는 구간이 실제로 얼마나 되는지 측정해보고, 그 결과를 보고 문제 크기를 판단한다 (아직 실행 안 함 — 다음에 진행)
  - 팜뮤트·고스트노트 자체의 정식 인식(음색·배음 구조 분석 필요)은 4-2 섹션에 이미 "후순위"로 정리되어 있어 지금 범위 밖
- **3-1. 완전 무음 구간(다른 악기 bleed)** — ✅ 방향 결정됨(구현은 아직 안 함):
  - 지금은 사용자가 "몇 초부터 몇 초까지 베이스 연주"라고 직접 알려주는 완전 수동 방식(color_mixed 작업 때 사용)
  - **반자동으로 전환**: bass.wav의 RMS 에너지 흐름을 분석해 "베이스가 실제 연주 중인 것 같은 구간"을 자동 추정 → 사용자에게 후보로 제시해 확인받는 방식. periodicity(피치 신뢰도)만으로는 안 됨 — bleed가 베이스와 비슷한 음역대 악기(기타 등)면 periodicity도 높게 나와 구분이 안 될 수 있어서, 에너지(음량) 기반이 더 안정적인 신호로 판단
  - **곡 중간에 다른 악기는 연주 중인데 베이스만 쉬는 구간 처리**: 노트가 없다고 마디 자체를 건너뛰면 안 되고, **빈 마디(쉼표)로 명시적으로 표기**해야 함. 현재 `build_musicxml`(`poc_export_musicxml.py`)이 노트가 하나도 없는 마디를 통째로 건너뛰는 구조라(color_mixed에서 마디 12부터 시작하고 1~11이 아예 없는 것처럼 처리된 원인) — 곡 전체 마디 범위(첫 비트~마지막 비트 기준)를 알고 그 안에서 노트 없는 마디는 전부 쉼표로 채우도록 구조를 바꿔야 함. 아직 구현 안 함, 다음 구현 작업 후보.
- **3-3. 피치 곡선만으로 판별 불가능한 주법(슬랩·하모닉스·팜뮤트)** — 가설만 정리, **구현은 보류**(다른 항목들을 먼저 완벽하게 끝낸 뒤 진행하기로 함):
  - 셋 다 음정(피치) 정보만으론 구분 안 되고 음색/스펙트럼 특징이 필요함
  - 슬랩: 타격 트랜지언트가 강함(어택이 날카롭고 순간적으로 고주파 에너지가 튐) → `librosa.onset.onset_strength` 후보
  - 하모닉스: 배음이 거의 없는 순수한 음색(기본음 대비 배음 에너지 비율이 매우 낮음) + 프렛 위치 대비 예상 밖의 음정 → 스펙트럼 평탄도 계열 분석 후보
  - 팜뮤트: 감쇠가 빠르고(서스테인 짧음) 음색이 어두움(고주파 성분 적음) → `librosa.feature.spectral_centroid`(음색 밝기) + 노트 길이 대비 감쇠 속도 후보
  - 새 라이브러리 도입 없이 기존 librosa로 시도 가능할 것으로 보이나, 계획서 4-2 섹션에서 이미 "후순위"로 분류한 영역과 일치 — 다른 품질 기준 항목(11-1·11-2·11-4·11-5)이 안정화된 뒤에 착수

### 11-4. 운지·슬라이드
- 아는 것: 포지션 박스 개념(`POSITION_SPAN` 등), 슬라이드 판정 3종 — 옥타브 슬라이드(`detect_octave_slides`)/크로매틱 런(`find_chromatic_runs`)/검증된 도약쌍(`detect_leap_slides`, `VALIDATED_LEAP_SLIDES`), 슬라이드 도착 위치를 다음 반복음에 전파하는 로직(`propagate_slide_landing`) — 전부 `poc_tab_render.py`의 `resolve_fingering()`에 통합됨
- 정할 것: `VALIDATED_LEAP_SLIDES` 같은 하드코딩 방식이 곡이 늘어날수록 감당되는지, 아니면 원본 피치 곡선(글리산도 연속성)으로 판단하는 더 일반적인 방법으로 언제 갈아탈지. 아직 미논의.

- 아는 것: 사용자가 직접 TAB을 고쳐서 diff로 대조하는 방식이 효과적이었음(color_mixed 작업에서 확인)
