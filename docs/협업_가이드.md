# 공동작업자 가이드

AI TAB 악보 앱 프로젝트(Phase 0 PoC)에 처음 합류하는 팀원을 위한 셋업·작업 방법 안내입니다.
프로젝트 배경과 기획은 [타브 악보 작업 계획서.md](타브%20악보%20작업%20계획서.md)를 먼저 읽어보세요.

## 1. 사전 설치

- **Python 3.13**
- **Git**
- **ffmpeg** — `winget install ffmpeg` (Windows)
- **Demucs**(음원 분리)는 아래 pip 설치에 포함되어 있음

## 2. 저장소 클론 및 셋업

```bash
git clone https://github.com/chldbfk/bass-copy.git
cd bass-copy
pip install -r requirements.txt
```

### alphatab_source 별도 clone (필요할 때만)

alphaTab 라이브러리 원본(152MB, 자체 .git 포함)은 저장소 용량 문제로 `.gitignore` 처리되어 있습니다.
악보 렌더링 결과물을 보는 것만으로는 필요 없고, alphaTab 자체를 빌드/수정할 때만 아래처럼 따로 받으세요.

```bash
git clone https://github.com/Coderline/alphaTab alphatab_source
```

평소 사용하는 빌드된 라이브러리(`alphatab_lib/alphaTab.min.js`, `Bravura.woff2`)는 저장소에 이미 포함되어 있어 별도 설치 없이 바로 씁니다.

## 3. 폴더 구조

```
bass-copy/
├── docs/                 # 기획서, 작업기록 등 문서
├── songs/<곡이름>/        # 곡별 원본 mp3 + outputs(결과물)
│   └── outputs/          # 파이프라인 실행 결과 (txt, musicxml, html)
├── alphatab_lib/          # 빌드된 alphaTab 뷰어 라이브러리 (커밋됨)
├── alphatab_source/       # alphaTab 원본 소스 (gitignore, 필요시 별도 clone)
└── poc_*.py               # 파이프라인 각 단계 스크립트
```

`songs/<곡이름>/separated/`(Demucs 음원 분리 중간 산출물)는 용량이 커서 gitignore 처리되어 있습니다. 아래 파이프라인을 로컬에서 실행하면 다시 생성됩니다.

## 4. 파이프라인 실행 순서

한 곡을 처음부터 처리하는 전체 흐름입니다. `<곡파일>.mp3` 자리에 실제 파일 경로를 넣으세요.

```bash
# 1) 음원 분리 (보컬/드럼/베이스/기타 분리) — Demucs CLI
demucs <곡파일>.mp3

# 2) 피치(음정) 추출 — 분리된 bass.wav 사용
python poc_pitch_extract.py separated/htdemucs/<곡이름>/bass.wav poc_output.txt

# 3) 리듬 정렬(BPM/박자 감지 및 양자화)
python poc_rhythm_quantize.py <곡파일>.mp3 poc_output.txt

# 4) TAB 렌더링 (스케일 필터링 + 운지 최적화)
python poc_tab_render.py poc_output.txt poc_tab_output.txt

# 5) 최종 TAB 텍스트 출력
python poc_final_tab.py <곡파일>.mp3 poc_output.txt poc_final_tab_output.txt

# 6) 악보 포맷으로 내보내기 (필요한 것 선택)
python poc_export_musicxml.py <곡파일>.mp3 poc_output.txt "<곡 제목>" poc_score.musicxml
python poc_export_alphatab_html.py <곡파일>.mp3 poc_output.txt "<곡 제목>" poc_score_alphatab.html
python poc_export_html.py <곡파일>.mp3 poc_output.txt "<곡 제목>" poc_tab_visual.html
```

BPM 자동감지 결과가 옥타브 단위로 어긋나 보이면(예: 실제 90인데 180으로 감지) 자동 신뢰하지 말고 수동 확인 후 보정하세요. 자세한 기준은 팀 내 공유된 BPM 보정 가이드를 참고하세요.

## 5. Git 협업 규칙

1. **작업 시작 전**: `git pull origin main`으로 최신 상태 받기
2. **기능/곡 단위로 브랜치 생성**: `git checkout -b <이름>/<작업내용>` (예: `yura/새곡-분석`)
3. 작업 후 `git add`, `git commit`, `git push origin <브랜치명>`
4. GitHub에서 Pull Request 생성 → 서로 리뷰 후 `main`에 merge
5. `main`에 직접 push하지 말고 PR을 거치는 것을 권장 (동시 작업 시 충돌 방지)

### 커밋 시 주의사항

- `songs/<곡이름>/separated/`, `alphatab_source/`는 이미 `.gitignore`에 등록되어 있으니 실수로 강제 추가(`git add -f`)하지 않기
- 새 곡을 추가할 땐 `songs/<곡이름>/` 폴더를 만들고 그 안에 원본 mp3와 `outputs/`를 정리해서 커밋 (루트에 파일을 흩어놓지 않기)
- 새 문서는 `docs/`, 새 곡 관련 파일은 `songs/`에 바로 생성 — 나중에 옮기지 않기
