# 파이프라인 회귀 테스트

새 곡을 처리하다 `poc_*.py` 파이프라인 코드를 고칠 때, 그 수정이 **이미 사람이 원곡과
대조해 검증해둔 예전 곡들의 결과를 조용히 깨뜨리지 않았는지** 자동으로 확인하는 스위트.

## 왜 필요한가

지금까지(Stand-By-Me, 돈룩백, 나는나비 등) 발견된 버그들 —
MusicXML 템포 태그 누락, 마디 앵커 밀림, ASCII 라벨 합계 불일치, 크로매틱 런 오적용 —
은 전부 **새 곡을 처리하다가 우연히 사람이 눈치채서** 발견됐다. 곡 수가 늘어날수록
"새 곡 고치다 옛날 곡이 깨지는" 걸 놓칠 위험도 커지므로, 검증 끝난 곡들을 고정 fixture로
등록해 코드를 고칠 때마다(또는 그냥 주기적으로) 자동 재검사한다.

## 무엇을 검증하는가

오디오 추출(Demucs 음원분리 + torchcrepe 피치추출)은 느리고 약간 비결정적이라 매번
다시 돌리지 않는다. 대신 **이미 추출·교정 완료된 notes.txt를 고정 입력**으로 삼아,
그 다음 단계(스케일 필터링 → 운지 최적화/슬라이드 → 리듬 정렬 → ASCII TAB/MusicXML
렌더링)만 검증한다 — 실제로 버그가 났던 계층이 전부 여기이기 때문.

두 가지를 확인한다:

1. **불변조건** (golden 유무와 무관하게 항상 검사): 각 마디의 ASCII 라벨 합계가
   정확히 4.0박인지, MusicXML에 `<sound tempo>` 태그가 실제 템포로 박혀 있는지.
2. **Golden 스냅샷 대조**: 노트 수·템포·조성·마디 수·슬라이드 그룹·ASCII TAB 전문·
   MusicXML 전문이 `golden/<곡이름>.json`과 정확히 같은지.

## 사용법

프로젝트 루트에서:

```bash
python tests/regression/run.py           # 검증만 — golden과 다르면 실패(exit 1)
python tests/regression/run.py --update  # 지금 결과를 새 golden으로 저장/갱신
```

**`--update`는 반드시 사람이 그 곡의 결과(마디 수·노트·슬라이드)를 원곡 또는 직접
만든 정답 TAB과 대조해 확인한 뒤에만 사용할 것.** 검증 없이 `--update`하면 틀린 결과가
그대로 "정답"으로 고정돼버려서, 이후 진짜 회귀가 나도 못 잡아낸다.

## 곡 추가하기

새 곡을 사용자와 함께 원곡 대조까지 끝냈다면 `fixtures.py`에 항목을 추가하고
(override_bpm 등은 반드시 명시적으로 고정 — 자동감지는 재실행마다 흔들릴 수 있음)
`python tests/regression/run.py --update`로 golden을 만든다.

## 알려진 미해결 버그를 다루는 법

가끔 "버그인 걸 알지만 근본 원인을 나중에 고치기로 미룬" 경우가 있다(예: 나는나비
마디4 라벨 합계 4.5박 — `_close_measure_labels()`의 한계, 디케이 과분절이 근본
원인이라 그것부터 고치기로 함). 이런 건 fixture의 `known_label_sum_issues`에
`{마디번호: 현재값}`으로 명시해두면, 그 값과 정확히 같을 때만 통과시키고 값이 더
벗어나면(개선이든 악화든) 다시 실패로 잡아낸다.
